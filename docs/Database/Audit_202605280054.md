## Scope

This is a blind database-structure audit of the current dev environment and the checked-in SQL/psql surface.

Reviewed:

No destructive action was run. I did not modify data, credentials, grants, schema, migrations, or human accounts.

## Executive Summary

The database is in decent shape for a fast-moving dev environment, but there are several issues that would become serious in staging/prod or under heavier load.

Top risks:

1. `schema_migrations` is out of sync with the migration files. The migration runner currently reports 39 pending `vector_artefacts` migrations even though many of the corresponding objects already exist.
2. The application DB role `mmff_dev` is a superuser with `CREATEDB`, `CREATEROLE`, `REPLICATION`, and `BYPASSRLS`.
3. The search-index pipeline is effectively broken: 139 outbox rows are stuck, 0 artefacts have `tsvector`, and 0 artefacts have embeddings.
4. The work-item list path has a recursive rollup CTE that is already the dominant slow query in `pg_stat_statements`.
5. There are 43 foreign keys without a supporting left-prefix index on the referencing columns.
6. There are 9 duplicate/equivalent indexes.
7. Notification v2 listens for `notifications_outbox_v2_inserted`, but the table has no trigger that emits that `pg_notify`.
8. API keys are mostly long-lived and many active keys have empty scope arrays.
9. `artefacts` has heavy bloat/free-space after churn: 28 MB table size for ~141 live rows, with `pgstattuple_approx` reporting ~97 percent free space.
10. Several dev scripts and comments still refer to `mmff_vector` as if it were active, creating operator risk after the cutover.

## Findings

### F001 - Critical - Migration ledger is out of sync with live schema

Evidence:

- `go run ./cmd/migrate -db vector_artefacts -dir .. -env .env.dev -dry-run` reports 39 pending migrations.
- Pending migrations include `093` through `130` and `137`.
- Live schema already contains objects from several of those pending files, for example `notifications_events_v2`, `notifications_outbox_v2`, and other notification v2 tables.
- `schema_migrations` currently records 96 migrations.
- Top-level `db/vector_artefacts/schema` contains 134 SQL files.
- `schema_migrations` has one applied filename that no longer exists in the top-level migration directory: `015_backfill_work_items.sql`.

Risk:

- Running the migration runner against dev can attempt to reapply migrations that are already structurally present.
- Best case: the runner fails on duplicate objects and blocks deploy.
- Worse case: partly idempotent files mutate data or grants twice before failing.
- This also destroys trust in `schema_migrations` as the source of truth for what the DB has actually received.

Proposed fix:

1. Freeze writes briefly.
2. For each pending migration, classify as:
   - already fully applied
   - partially applied
   - truly pending
3. For fully applied files, insert the exact filename into `schema_migrations` with the real/estimated applied timestamp.
4. For partially applied files, write a one-off reconciliation migration that brings the object to the checked-in definition, then mark the original file applied.
5. For truly pending files, apply normally.
6. Add a CI/dev gate: `go run ./cmd/migrate -db vector_artefacts -dir .. -env backend/.env.dev -dry-run` must print "up to date" before a merge.
7. Add a migration-ledger audit script that compares top-level `*.sql` files against `schema_migrations` and fails on drift.

Suggested owner:

- Database/platform.

### F002 - Critical - App DB role is superuser and bypasses every database guard

Evidence:

Role attributes for `mmff_dev`:

- `rolsuper = true`
- `rolcreaterole = true`
- `rolcreatedb = true`
- `rolreplication = true`
- `rolbypassrls = true`
- `rolcanlogin = true`

Risk:

- Any SQL injection, leaked DSN, compromised dev helper, or accidental shell command has full cluster privileges.
- RLS, if added later, would be bypassed by the current app role.
- A dev application bug can create/drop DBs, create roles, read every schema, bypass future row-level policies, and use replication privileges.

Proposed fix:

1. Split roles:
   - `vector_app` - login, least privilege DML only on app tables.
   - `vector_migrator` - DDL rights, no app runtime use.
   - `vector_readonly` - inspection/reporting only.
   - `vector_library_ro` - read-only library access.
2. Stop running the backend with `mmff_dev`.
3. Keep `mmff_dev` only as a local/dev owner or replace it with a non-login owner role.
4. Rotate the credentials after role split.
5. Add a startup check that refuses to run app HTTP server when `current_user` has `rolsuper = true`, except behind an explicit local-only development override.

Suggested owner:

- Platform/security.

### F003 - High - FDW user mapping stores a reusable DB password in database catalog

Evidence:

- `vector_artefacts` has FDW server `fdw_mmff_library`.
- `pg_user_mappings` contains a mapping for `mmff_dev` with a password option.
- No `mmff_vector` foreign tables remain, but `postgres_fdw` remains for library cross-DB reads.

Risk:

- A superuser or sufficiently privileged DB actor can inspect or misuse the mapping.
- The mapping uses the same broad `mmff_dev` identity rather than a narrow read-only role.
- A compromise of `vector_artefacts` becomes a path into `mmff_library`.

Proposed fix:

1. Replace the FDW mapping with a dedicated `mmff_library_ro` mapping, never `mmff_dev`.
2. Store only the minimum read-only grants needed by the FDW.
3. If FDW is not used in active code, remove the server, mapping, and `postgres_fdw` extension from `vector_artefacts`.
4. If FDW remains, document the cross-DB dependency and add a canary that verifies no mapping uses a superuser.

Suggested owner:

- Platform/security.

### F004 - High - Search indexing is broken and the queue is stuck

Evidence:

- `artefacts_search_outbox` rows: 141 total.
- Unclaimed rows: 139.
- Rows with attempts >= 5: 139.
- Error sample:
  - `embed: Post "http://localhost:11434/api/embeddings": dial tcp [::1]:11434: connect: connection refused`
  - `embed: ollama HTTP 404`
- Artefacts indexed:
  - total artefacts: 141
  - `artefacts_search_index IS NOT NULL`: 0
  - `artefacts_content_embedding IS NOT NULL`: 0

Risk:

- Full-text and semantic search are effectively empty.
- The worker keeps polling a queue that cannot currently drain.
- Search-related UX will look like no data exists, not like an indexer is down.
- The queue can become permanent noise, hiding new failures.

Proposed fix:

1. Split text indexing from embedding generation:
   - Always compute/write `artefacts_search_index` locally with Postgres `to_tsvector`.
   - Treat embeddings as optional enrichment.
2. Add dead-letter state for embedding failures after `maxAttempts`.
3. Add worker health metrics:
   - queue depth
   - oldest unclaimed row age
   - attempts >= max
   - last successful embedding time
4. Fix `OLLAMA_URL`/model configuration or disable embeddings explicitly in dev.
5. Add an admin repair endpoint or script to requeue failed embedding rows after the embedding service is restored.

Suggested owner:

- Search/platform.

### F005 - High - Recursive story-point rollup query is already the slowest app query

Evidence from `pg_stat_statements`:

- Recursive `rollup_points` query variants show mean execution times around:
  - 519 ms
  - 215 ms
  - 93 ms
- One variant accumulated 31.8 seconds total execution time.
- The query is used by `backend/internal/artefactitems/sql.go`.
- The CTE recursively scans descendants for each parent row in the list path.

Risk:

- This will degrade fast as artefacts grow from hundreds to thousands.
- Work-item list, filtering, and sorting by points become expensive.
- The query repeats hierarchy traversal work on every list request.

Proposed fix:

1. Add persisted rollup fields to `artefacts`, for example:
   - `artefacts_rollup_story_points`
   - `artefacts_children_count`
   - `artefacts_rollup_updated_at`
2. Maintain them incrementally when story points, parent, archive state, or flow state changes.
3. If persisted columns feel too invasive, use a materialized view over the hierarchy and refresh/debounce after artefact writes.
4. Keep the recursive CTE only for repair/rebuild jobs, not hot list reads.
5. Add an `EXPLAIN (ANALYZE, BUFFERS)` benchmark before and after.

Suggested owner:

- Work-items/backend.

Evidence:

Live query found 43 FKs where the referencing columns are not covered by an exact or left-prefix valid index.

Examples:

- `artefacts.artefacts_id_artefact_type -> artefacts_types`
- `artefacts.artefacts_id_priority -> artefact_priorities`
- `artefacts_number_sequences.artefacts_number_sequences_id_artefact_type -> artefacts_types`

### F012 - Medium - Database does not enforce tenant isolation with RLS

Evidence:

4. Keep Sentinel as the app owner of identity/scope, but let Postgres reject missing or wrong scope as a second gate.

## Appendix - Useful Verification Queries

Migration drift:

```sql
SELECT filename FROM schema_migrations ORDER BY filename;
```

Foreign keys without referencing index:

```sql
WITH fk AS (
  SELECT con.oid, con.conrelid, con.conname, con.conkey,
         con.conrelid::regclass AS table_name,
         con.confrelid::regclass AS referenced_table,
         array_agg(att.attname ORDER BY u.ord) AS columns
  FROM pg_constraint con
  JOIN unnest(con.conkey) WITH ORDINALITY AS u(attnum, ord) ON true
  JOIN pg_attribute att ON att.attrelid = con.conrelid AND att.attnum = u.attnum
  WHERE con.contype = 'f'
  GROUP BY con.oid, con.conrelid, con.conname, con.conkey, con.confrelid
)
SELECT fk.table_name, fk.conname, fk.columns, fk.referenced_table
FROM fk
WHERE NOT EXISTS (
  SELECT 1
  FROM pg_index i
  WHERE i.indrelid = fk.conrelid
    AND i.indisvalid
    AND (i.indkey::int2[])[0:array_length(fk.conkey, 1)-1] = fk.conkey
)
ORDER BY fk.table_name::text, fk.conname;
```

Duplicate indexes:

```sql
WITH idx AS (
  SELECT indexrelid AS idx, indrelid, indkey, indclass, indoption,
         coalesce(indexprs::text, '') AS exprs,
         coalesce(indpred::text, '') AS pred
  FROM pg_index
  WHERE indisvalid
)
SELECT pg_size_pretty(sum(pg_relation_size(idx))::bigint) AS total_size,
       array_agg(idx::regclass::text ORDER BY idx::regclass::text) AS indexes
FROM idx
GROUP BY indrelid, indkey, indclass, indoption, exprs, pred
HAVING count(*) > 1
ORDER BY sum(pg_relation_size(idx)) DESC;
```

Search queue state:

```sql
SELECT
  count(*) AS total,
  count(*) FILTER (WHERE artefacts_search_outbox_claimed_at IS NULL) AS unclaimed,
  count(*) FILTER (WHERE artefacts_search_outbox_attempts >= 5) AS attempts_5_plus
FROM artefacts_search_outbox;
```

Session hygiene:

```sql
SELECT count(*) AS sessions_total,
       count(*) FILTER (WHERE users_sessions_expires_at < now()) AS expired,
       count(*) FILTER (WHERE users_sessions_revoked) AS revoked
```
